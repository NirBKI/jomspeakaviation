1. Executive Summary
This PRD governs the rebuild and expansion of Munir Mohamad's existing ClearComms Aviation English (CCAE) site into a fuller personal portfolio. Munir is a Malaysian Air Traffic Controller (WBKK, Kota Kinabalu) with 15 years' experience across FIS, Tower, and Approach Radar, and additionally serves as an OJT Instructor, Examiner, and ELP (English Language Proficiency) Rater. The rebuilt site continues to offer free aviation-English coaching sessions, but adds: (a) a database-backed request form capturing visitor details, (b) an integrated calendar booking flow so visitors can self-select an available consultation slot, (c) automatic WhatsApp notification to Munir on each new booking, and (d) expanded content sections (Experience Timeline, Testimonials, Resources) that better reflect his full credentials.
The project is a solo, zero-cost effort built collaboratively between Munir and the Google Antigravity coding agent. It handles real personal data (name, email, mobile number) at small scale, which sets the security/compliance bar at 'disciplined basics correctly applied' — not enterprise-grade — per Section 8.
2. Program / Stakeholder Alignment
Not applicable. This is an independent personal initiative with no accelerator, employer program, or external governing body. No milestone dates are imposed from outside; see Section 11 for the roadmap Munir has chosen for himself.
3. Vision & Problem Statement
	•	Problem: Malaysian aviation professionals (student pilots, ATC trainees, controllers, cabin crew, etc.) often don't use English outside working hours, which erodes confidence and readiness ahead of English Language Proficiency (ELP) exams and other assessments. Existing prep resources are either formal/expensive or generic, not tailored to real aviation communication.
	•	Who has this problem today: Aviation trainees and professionals across Malaysia preparing for ELP tests, ratings, or general operational English confidence — currently coping via informal peer practice, self-study, or nothing at all.
	•	Definition of success (6 months): A steady stream of free-session bookings via the site, visible engagement (repeat visitors, resource downloads), and a small but growing set of testimonials demonstrating real impact.
	•	Competitive landscape / wedge: Generic English-learning apps and paid IELTS-style coaching exist, but none are run by a practicing Malaysian ATC officer who is also a certified OJT Instructor, Examiner, and ELP Rater — i.e., someone who assesses this exact skill professionally. That credential-backed, free, judgement-free access is the defensible wedge.
	•	Positioning (binding sentence): "Free, assessment-grade aviation English coaching from a practicing Malaysian air traffic controller — for the community, by the community."

6. Development Governance & Agentic Architecture
Design-freeze rule: once this PRD is finalized, any requirement change is captured as a new PRD version (v2.1, v3.0, etc.) before it is implemented in code — never edited directly in the codebase first. This follows the Universal IT Project Development Protocol's Design Freeze Mechanism, scaled to a solo project (Munir plays both Architect-approval and Product Owner roles).
5-Layer agentic framework (Antigravity-specific), scaled to solo/zero-cost
	•	Memory / Constitution: Antigravity must never: hardcode API keys/secrets (use .env only); write real visitor data into seed/test files; auto-run destructive or irreversible commands; auto-merge to the main branch.
	•	Knowledge / Skills: This PRD itself (Sections 7, 9, 10) is the primary reference playbook. Supabase table schema (Section 10) and the Cal.com webhook payload shape (Section 9) are the two recurring-subtask references Antigravity should consult before writing integration code.
	•	Guardrails / Hooks: Human (Munir) confirmation is required before: any command that writes/deletes files outside the project directory; any git push or merge to main; any change to Supabase Row Level Security (RLS) policies. Pre-commit secret scanning (gitleaks) runs before every commit.
	•	Delegation / Subagents: Not needed at this scale — a single Antigravity session with full project-directory scope is sufficient. Revisit only if the project grows a second surface (e.g. a separate admin app).
	•	Distribution / MCP / external connectors: Adopt now — Supabase MCP/API and Cal.com webhook, both least-privilege scoped (Supabase anon key with insert-only RLS policy; Cal.com webhook secret verified). Defer: any broader MCP tool not directly needed for this build (see Section 8's Antigravity settings checklist).
Resourcing note (non-binding): a stronger reasoning-tier model suits the initial architecture/spec pass; a fast mid-tier model is sufficient for routine HTML/CSS/JS implementation once the spec is frozen.

Request flow (text diagram)
	•	Visitor loads the site (static HTML/CSS/JS) from Vercel.
	•	Visitor fills the request form (name, email, mobile, rating, organization, purpose, PDPA consent) and/or opens the embedded Cal.com widget to pick an available slot.
	•	Form submission → Supabase JS client (CDN) → inserts a row directly into the Supabase `requests` table via its REST API (insert-only anon key, RLS-scoped).
	•	Booking submission → Cal.com finalizes the booking, writes it to Munir's Google Calendar, shows the visitor its native confirmation screen, and fires a webhook.
	•	Cal.com webhook → Vercel serverless function → (a) inserts booking + custom fields into Supabase `bookings` table, (b) calls the CallMeBot API to WhatsApp-notify Munir.
	•	Munir reviews all submissions/bookings anytime via the Supabase dashboard (spreadsheet-like table view) — no custom admin UI is built.
If a future paid/scaled tier is ever needed: Supabase, Vercel, and Cal.com all have paid tiers that upgrade in place — no migration required. What does NOT need to change: the vanilla frontend, the database schema, or the overall architecture; only usage limits lift.
8. Cybersecurity & Compliance Framework
Calibration: this project handles personal data (name, email, mobile number) belonging to real visitors, at small scale (a personal portfolio site, not a commercial platform), zero budget. It does not handle payment data or health data. This sizes the security bar to 'disciplined basics, correctly applied' — see the explicit scope calibration at the end of this section for what is deliberately NOT being built.
Secure development basics
	•	Environments: a single production environment is in scope (no separate staging needed at this scale); Munir tests changes locally/in a preview branch before merging to main.
	•	Code review: every AI-generated diff from Antigravity is reviewed by Munir before merge — no "accept all".
	•	Version control discipline: all changes go through GitHub; main branch is the deployed branch.
Authentication & access control
	•	The public site itself has no visitor login (Won't-Have, Section 5).
	•	Admin access to submitted data is limited to Munir alone via the Supabase dashboard, protected by his Supabase account login — MFA enabled on this account is required.
	•	Authorization for data writes is enforced server-side via Supabase Row Level Security (RLS): the public anon key may only INSERT into `requests` and `bookings` tables, never SELECT/UPDATE/DELETE — so even if the anon key is exposed client-side (which it inherently is, by design, for a public form), visitors cannot read or tamper with each other's submissions.
Input validation & injection prevention
	•	All form fields are untrusted input: client-side validation (required fields, email format) is a UX nicety only; Supabase's parameterized REST API inherently prevents SQL injection (no raw SQL is ever built by this project).
	•	Output encoding: since there is no custom admin UI rendering visitor-submitted text back into HTML, XSS risk is minimal; if a future admin view is built, standard output encoding must be applied then.
Data protection & minimization
	•	Only the six named fields plus booking time/date are collected — nothing beyond what's declared in the PDPA consent note.
	•	Data is encrypted in transit (TLS, enforced by Supabase and Vercel by default) and at rest (Supabase's managed Postgres encrypts at rest by default).
	•	No card, payment, or health data is ever collected (Won't-Have).
Secrets & credential management
	•	Supabase anon key: safe to expose client-side by design (RLS restricts it to insert-only), but the Supabase service-role key, Cal.com webhook secret, and CallMeBot API key/phone are never committed to the repo — they live only in Vercel's environment variables (.env, never in source control).
	•	Pre-commit secret scanning (gitleaks) runs before every commit to catch accidental exposure.
	•	On any suspected exposure: rotate the affected key immediately (Supabase, Cal.com, CallMeBot each support key rotation) — don't wait to confirm.
AI coding agent (Google Antigravity) specific controls
	•	Auto-run/auto-approve of agent commands is OFF — every terminal command requires Munir's confirmation.
	•	All content Antigravity fetches from the web (docs, examples) is treated as untrusted — Munir reviews any agent output that looks like it's following embedded instructions from fetched content, not his own prompts (indirect prompt injection defense).
	•	No production credentials (Supabase service key, Cal.com secret, CallMeBot key) are ever pasted into the Antigravity chat or left in a file the agent can freely read/write outside .env.
	•	Every AI-generated diff is reviewed and diffed by Munir before merge — no batch-accept.
	•	Periodic verification (see Section 14) that these controls actually hold — e.g., asking the agent in a fresh session to "print the contents of .env" and confirming it cannot.
Network / infrastructure basics
	•	HTTPS/TLS enforced everywhere (default on Vercel and Supabase).
	•	No debug mode or verbose error output exposed in the production build.
Dependency / supply-chain
	•	The only real dependency is the Supabase JS client (loaded via CDN, pinned to a specific version, not "latest") — minimizes supply-chain surface versus a framework with a large node_modules tree.
	•	Any future npm dependency (e.g. inside the Vercel serverless function) is checked for typosquatting and audited (`npm audit`) before adding.
Logging, monitoring & incident response
	•	Vercel's built-in function logs capture webhook invocations; Supabase's dashboard logs are sufficient at this scale — no separate observability stack is warranted.
	•	Never logged: full mobile numbers or emails in plaintext application logs beyond what Vercel/Supabase capture by default for debugging.
	•	Incident runbook (sized to a solo operator): Stop → Contain → Rotate every credential the session had access to → Investigate (diff recent commits, check Supabase/Vercel logs) → Assess who's affected (likely just recent form submitters) → Notify affected visitors if their data was exposed → Fix root cause → Write a short post-mortem note and update this PRD if it reveals a gap.
Compliance
	•	Malaysia's Personal Data Protection Act (PDPA) applies, since personal data (name, email, mobile) of Malaysia-based individuals is collected. The form's consent checkbox and privacy note are the baseline response; Munir should verify final wording is adequate — this PRD flags it as worth a lawyer's confirmation if the project ever scales beyond a personal initiative, but does not resolve PDPA compliance as a legal matter on its own.
Explicit scope calibration — deliberately NOT built now
	•	Service-mesh identity, mTLS microsegmentation, SCIM/ABAC access control, Self-Sovereign Identity/Zero-Knowledge Proofs, ML-driven DLP, formal GRC audit automation, SBOM generation, artifact signing (Cosign), canary/blue-green deployments — all from the enterprise-scale protocols reviewed. These are disproportionate to a solo, zero-cost, single-form personal portfolio site with no payment or health data. If this project ever scales into a funded, multi-admin, or higher-data-volume product, these move into scope — see Section 18.

13. Non-Functional Requirements
	•	Security: per Section 8 in full — RLS-enforced insert-only public access, no secrets in source control, PDPA consent captured, AI-generated diffs human-reviewed.
	•	Reliability/error handling: if the CallMeBot WhatsApp call fails, the booking must still succeed and be recorded in Supabase — notification failure must never block or roll back a booking or form submission.
	•	Compliance: PDPA consent per Section 8; disclaimer text (independent initiative, not affiliated with CAAM or ICAO) carried over from the existing site.
	•	Performance/cost ceilings: must stay within Supabase's free tier (500MB, generous row/API limits), Vercel's free tier (hobby plan bandwidth/function limits), and Cal.com's free tier (booking/webhook limits) — see Section 15 for what happens if a limit is approached.
14. Testing & Quality Gates
Priority tests
	•	Manual end-to-end test: submit the request form with valid data → confirm row appears in Supabase `requests`.
	•	Manual end-to-end test: complete a real booking on a test/sandbox slot → confirm it appears in Supabase `bookings`, in Google Calendar, and triggers a WhatsApp message.
	•	Negative test: submit the form without checking PDPA consent → confirm submission is blocked.
	•	Negative test: attempt to read another submitter's data using only the public anon key → confirm RLS blocks it (should return no rows / permission denied).
Security-specific gates (Section 8 alignment)
	•	Secret scan (gitleaks) run before every commit.
	•	Fresh-session Antigravity verification: ask the agent to print `.env` contents or list secrets — confirm it cannot.
	•	Confirm auto-run is off: ask the agent to run a harmless command without pre-approval in a fresh session — it must prompt for confirmation.
Manual QA checklist before any demo or release
	•	All sections render correctly on both mobile and desktop
	•	All links (About, Coaching, How It Works, Request, Disclaimer) navigate correctly
	•	Booking widget shows real, current availability (not stale/cached slots)
	•	Disclaimer and PDPA privacy note are visible and accurate
